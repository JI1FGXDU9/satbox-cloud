# SatBox Cloud サーバー設置手順

## 1. 対象と設置方式

本書はLinux系のレンタルサーバーでSatBox Cloudを公開するための手順です。
XSERVERの設置例を含みますが、他社の共有サーバー、Python対応ホスティング、
VPSでも、以下の要件を満たす環境で利用できます。
さくらのレンタルサーバ、ロリポップ！などを検討する場合も、事業者名だけで
判断せず、契約プランごとのPython・CGI・SSH・Cron対応と利用条件を確認してください。
本書は各社・各プランでの動作を保証するものではありません。

方式A：共有サーバーのPython CGI
```text
ApacheのCGI実行とURL書換えを使用します。公開入口はindex.cgiと.htaccessです。
同梱のdeploy/xserver-public/はXSERVER用のひな形です。別環境では修正が必要です。
.htaccessが使えない環境では、サーバー側で同等のルーティングを設定します。
```

方式B：WSGI／VPS
```text
Pythonアプリを実行できるホスティング、または常駐プロセスを許可するVPS向けです。
serve_web.pyでWaitressを起動し、HTTPSリバースプロキシ経由で公開できます。
CGIとWaitressを同じ公開入口に重ねて使用しません。
```

PHPだけのプランや静的HTML専用サービスでは、そのままでは動作しません。
FTPはファイル転送用です。Python環境・ライブラリ・定期実行の設定も別途必要です。

## 2. サーバーに必要な機能

- requirements-web.txt等の依存ライブラリが動くPython環境とvenv/pip。
```text
既存XSERVER環境はユーザー導入のPython 3.12を使用しています。
```
- Skyfield、SGP4、NumPy、Flask、SQLite、暗号／Web Push関連ライブラリ。
- SSH、または仮想環境作成と依存ライブラリ導入ができる同等の機能。
- 方式AではPython CGI、URL書換え、実行パーミッション設定。
- 方式BではWSGI公開機能、またはWaitressとHTTPSプロキシを運用できる権限。
- HTTPS、非公開フォルダーへの読み書き、SQLiteファイルのロック。
- AMSATのTLE取得先とWeb Push配信先への外向きHTTPS通信。
- 画面を閉じても通知する場合はCron等の定期実行、または許可された常駐処理。

共有サーバーではCPU・メモリ・CGI実行時間に制限があります。
多くの衛星を選ぶと初回計算が長くなるため、少数から開始してください。
Cronの最短間隔、常駐処理の可否、バックグラウンドプロセスの制限は事業者に確認します。

## 3. フォルダー配置と転送するファイル

以下は例です。ACCOUNT、DOMAIN、公開フォルダー名は実際の環境へ置換してください。

```text
アプリ本体（非公開）： /home/ACCOUNT/DOMAIN/satbox-cloud/
データ（非公開）：     /home/ACCOUNT/satbox-data/
公開入口（方式A）：   /home/ACCOUNT/DOMAIN/public_html/satbox/
公開URL：             https://DOMAIN/satbox/
```

サーバーによって公開フォルダー名はpublic_html、www、htdocsなど異なります。
アプリ本体とデータは、ブラウザーから直接ダウンロードできない場所へ配置します。

アプリ本体へ転送する主なファイル：
```text
satbox_web/、satbox_orbit/、satbox_notifications/、satbox_db.py
web-qth.json、nasa.all、iss-qth.source.json（更新日時メタデータ）
requirements.txt、requirements-web.txt、requirements-xserver.txt
setup_push.py、setup_admin.py、manage_admin.py
prepare_notifications.py、send_notifications.py
serve_web.py、notification_workers.sh、deploy/
```

web-qth.jsonのtle_fileとtle_metadata_fileが実際のファイル名に一致することを確認します。
templates/とstatic/はsatbox_web/内の構成を維持して転送します。
__pycache__、ローカルの.venv、backup、tests、ログ、更新用ZIPは通常転送しません。
サーバー上の既存.venv、DB、session.key、Web Push鍵を更新ファイルで上書きしないでください。
更新前にサーバー上のアプリと非公開データをバックアップします。

## 4. Python環境と依存ライブラリ

SSHでアプリ本体へ移動し、初回のみ仮想環境を作成します。
python3は、利用するPython実行ファイルのパスへ置換できます。

```text
cd /home/ACCOUNT/DOMAIN/satbox-cloud
python3 -m venv .venv
.venv/bin/python -m pip install -r requirements-web.txt
.venv/bin/python -c "import flask, skyfield, sgp4, numpy; from satbox_db import sqlite3; print(sqlite3.sqlite_version)"
```

既存XSERVERの旧Linux／ユーザー導入Python 3.12環境では、通常版のNumPyの
ビルドが通らない場合があるため、既存環境用のrequirements-xserver.txtを使用します。

```text
.venv/bin/python -m pip install --only-binary=numpy,pysqlite3-binary -r requirements-xserver.txt
```

この依存ファイルをすべての他社サーバーへ一律適用しないでください。
Pythonバージョン、OS、CPU、利用可能なwheelに合う依存ファイルを選びます。
satbox_db.pyは標準SQLiteが使えない場合にpysqlite3へ切り替えます。
既存環境で必要なライブラリが導入済みなら、変更がなければ再導入は不要です。

## 5. 非公開データの場所を統一

Web画面、管理コマンド、予定生成、送信処理は同じデータフォルダーを使用します。
例：

```text
export SATBOX_DATA_DIR=/home/ACCOUNT/satbox-data
mkdir -p "$SATBOX_DATA_DIR"
chmod 700 "$SATBOX_DATA_DIR"
```

CGIはSSHやCronの環境変数を自動で引き継ぐとは限りません。
方式Aでは公開index.cgiのimport osの後、アプリ読み込み前に以下を設定します。

```text
os.environ['SATBOX_DATA_DIR'] = '/home/ACCOUNT/satbox-data'
```

方式Bではホスティング／サービスの環境変数に同じ値を設定します。
Cronでも同じ値を設定するか、対応コマンドに--data-dirで明示します。
未指定時はユーザーデータ領域へ自動保存されますが、実行ユーザーや配置の違いで
別のDBを使用しないよう、設置時には場所を明示する方法を推奨します。

## 6. 方式A：CGI入口の設置

deploy/xserver-public/index.cgiと.htaccessを公開入口へ配置します。
上書き前に、設置先が別アプリのフォルダーでないことを確認してください。
公開入口へアプリ本体・DB・鍵をコピーする必要はありません。

index.cgiで変更する項目：
```text
先頭の#!行： /home/ACCOUNT/DOMAIN/satbox-cloud/.venv/bin/python
sys.path.insertのパス： /home/ACCOUNT/DOMAIN/satbox-cloud
SATBOX_DATA_DIR： 上記の非公開データフォルダー
BLASスレッド数を1にする設定はそのまま残します。
```

satbox_web/cgi_entry.pyで変更する項目：
```text
HTTPS転送先の固定'https://ji1fgx.com'を実際の'https://DOMAIN'へ変更。
公開パスが/satbox/以外ならnormalize_environmentのmount既定値と
SESSION_COOKIE_PATHを変更。
```

.htaccessで変更する項目：
```text
公開パスが異なる場合はRewriteBase /satbox/を変更。
CGIハンドラー等は事業者の仕様に合わせます。
ドメイン直下など既存の.htaccessを不用意に置換しないでください。
```

CGIファイルはLF改行・UTF-8 BOMなしで保存／転送します。
XSERVERではCGIと設置ディレクトリに755または705が指定されています。
例として755を使用する場合：

```text
chmod 755 /home/ACCOUNT/DOMAIN/public_html/satbox
chmod 755 /home/ACCOUNT/DOMAIN/public_html/satbox/index.cgi
chmod 644 /home/ACCOUNT/DOMAIN/public_html/satbox/.htaccess
```

他社では指定のパーミッションを使用します。777は必要ありません。
方式Aではserve_web.py／Waitressを起動しません。

## 7. 方式B：WSGI／VPSでの公開

ホスティングにWSGIアプリ指定欄がある場合は、事業者の手順に従い、例えば
satbox_web.app.create_app()の戻り値をapplicationとして公開します。
その方式では公開URL、HTTPS、サブパス、セッションCookieの設定も確認します。
HTTPS専用運用ではSATBOX_COOKIE_SECURE=1を設定してください。

自分でリバースプロキシを運用する場合の起動例：

```text
cd /home/ACCOUNT/DOMAIN/satbox-cloud
export SATBOX_DATA_DIR=/home/ACCOUNT/satbox-data
.venv/bin/python serve_web.py --port 8080
```

serve_web.pyは127.0.0.1で待ち受けます。同じホストの信頼できるHTTPSプロキシ
1段を想定し、X-Forwarded-Protoとサブパス用X-Forwarded-Prefixを使用します。
プロキシがこれらのヘッダーを正しく設定し、クライアントから来た値を引き継がない
ようにします。複数段プロキシの場合は構成に応じた調整が必要です。
本番では事業者の起動管理、またはsystemd等で再起動・ログ管理を行います。

## 8. 初回確認と管理者設定

HTTPSの公開URLを開き、以下を確認します。
```text
ログイン → 日本語／English選択 → ユーザー登録 → QTH設定
衛星選択 → Pass一覧 → 通知設定 → 通知予定
地図表示、LOCAL／GMT表示、ページ再表示後の言語保持
```

自分のアカウント登録後、初期管理者を設定します。

```text
cd /home/ACCOUNT/DOMAIN/satbox-cloud
.venv/bin/python setup_admin.py YOUR_LOGIN_ID --data-dir /home/ACCOUNT/satbox-data
```

YOUR_LOGIN_IDを実際のログインIDへ置換します。初期管理者が既にある場合は
管理画面やmanage_admin.pyを使用します。
管理画面のNASA.ALL更新は全ユーザー共通です。TLE更新日時は保存日時を表示します。

## 9. HTTPS、キャッシュ、地図

ログイン情報・QTH・通知登録情報は共有キャッシュに保存させません。
アプリはCache-Control: no-storeを付けます。サーバー／CDN側でも公開経路を
キャッシュ対象から除外します。XSERVERではXアクセラレータ等の設定を確認します。
JavaScript更新後はCtrl+F5等で再読み込みします。

地図はLeafletとOpenStreetMapの外部配信を使用します。
タイルの出典表示と参照元送信を維持し、配信元の利用条件を守ってください。
satellite-map.jsのタイル用referrerPolicy設定を削除すると403になる場合があります。
地図は観測点を中心に固定し、選択した衛星を通過中に表示します。

## 10. Web Pushの設定

画面が動作した後、同じ非公開データフォルダーで鍵と公開URLを設定します。

```text
.venv/bin/python setup_push.py --base-url https://DOMAIN/satbox --subject mailto:YOUR-EMAIL --data-dir /home/ACCOUNT/satbox-data
```

DOMAINとYOUR-EMAILを実際のドメインと連絡先へ置換します。
公開パスを変えた場合はbase-urlも変更してください。
スマートフォン／PCでHTTPSページへログインし、「通知端末登録」で登録します。
/satbox/設置の場合、Service Workerのscopeは/satbox/、通知クリック先は
/satbox/pass/<id>です。ブラウザーやOSの通知許可も必要です。
既存運用の鍵を不用意に作り直したり、別環境の鍵で上書きしないでください。

## 11. 予定生成と通知送信

画面公開だけでは、画面を閉じた後の通知を定期送信できません。
以下を、同じ設定ファイルとデータフォルダーで定期実行します。

```text
.venv/bin/python prepare_notifications.py --data-dir /home/ACCOUNT/satbox-data
.venv/bin/python send_notifications.py --data-dir /home/ACCOUNT/satbox-data
```

Cronでは作業ディレクトリをアプリ本体にし、Pythonの絶対パスを指定します。
ログは非公開フォルダーに保存し、重複起動を避けます。
送信の実行間隔が1分なら、その間隔による最大約1分の待ち時間に加え、
通信や端末側の遅延が発生し得ます。送信対象の期限はsend_notifications.pyと
通知ストレージの実装を確認し、Cronの間隔に注意してください。

常駐が許可されるLinux環境では、両コマンドの--loop、または付属の
notification_workers.shを使用できます。同スクリプトはbash、flock、Linuxの/proc、
アプリ内の.venv/bin/pythonを使用します。

```text
export SATBOX_DATA_DIR=/home/ACCOUNT/satbox-data
bash notification_workers.sh start
bash notification_workers.sh status
```

サーバー再起動後の自動起動は事業者の機能／systemd等で別途設定します。
共有サーバーで常駐を禁止している場合はこの方式を使わず、許可されたCron等で運用します。

## 12. エラー確認と更新時の注意

500エラー：サーバーのCGI／アプリログで、Pythonパス・モジュール・改行・権限を確認。
404／転送先違い：公開パス、RewriteBase、固定ドメイン、mountを確認。
ユーザーが見つからない：Web／Cron／コマンドのSATBOX_DATA_DIRを確認。
通知が来ない：端末登録、ブラウザー許可、通知条件、予定生成・送信処理とログを確認。
地図が403：参照元設定とタイル配信元の利用条件を確認。

アプリ更新時は変更ファイルを構成どおりに転送します。
CGI方式は通常Webプロセスの再起動不要です。WSGI／Waitress方式は再起動します。
通知workerのコードを更新した場合は、そのworkerも再起動します。
DB・鍵・セッションファイルは非公開で保管し、バックアップからの復旧方法も確認します。
